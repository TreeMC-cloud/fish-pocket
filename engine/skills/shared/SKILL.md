# 共享层 —— 四块板，各回答一个问题

文件来源：移植自 luanyujia-workbench 二-标准化规范 §6.7.1（记忆分两级）

多个场景并行时，有些东西不属于任何单一场景：待办、通知、索引、体检结果。

**关键不是"分层"，是每块板只回答一个问题。**

---

## 四块板

| 板 | 回答 | 谁写 | 更新频率 |
|---|---|---|---|
| **待办板** | 该做什么 | 任何场景加一行 | 每天几条 |
| **通知板** | 发生了什么 | 发通知的人 | 一天几十条 |
| **总索引** | 东西在哪 | 新建/移动时登记 | 一周几条 |
| **体检结果** | 机器健康吗 | 体检工具 | 一周一次 |

---

## 为什么必须分开

一位实践者给了三条真实教训：

**1. 淹没**
> 「看板一天几十条，一周就把索引和体检顶到看不见的地方。之后没人再往下翻——读的那件事自然就停了。」

**2. 责任糊掉**
> 「写在一块文件里，就没有『这块归谁写』这回事了。结果是想写的怕写错、该写的等人写，最后谁都不写。」

**3. 结构被迫统一**
> 「一块文件只能有一种写法。但『发生了什么』是流水、『东西在哪』是台账、『健康吗』是快照——硬塞进一种结构，三边都别扭。」

**判据：两块内容的更新频率差一个量级，或读者不是同一批人 ⇒ 必须分开。**

反过来也成立：频率和读者都接近的，**不要为了"看起来整齐"硬拆**。

## 待办板

```sh
node "$DSH_TOOLS/shared/shared.mjs" board              # 看未完成的
node "$DSH_TOOLS/shared/shared.mjs" board add <文字>   # 加一条
node "$DSH_TOOLS/shared/shared.mjs" board done <id>    # 划掉
```

**规则：做完就划掉，保持空白。**

> 他的原话：「它不是像很多观众想的一样是一个累积的大文件。每个场景做完了之后，就会把自己的东西给划掉，它就变成清清爽爽的一个空白文档。」

同一件事只许一行——加重复的会被拒绝。

---

## 通知板

```sh
node "$DSH_TOOLS/shared/shared.mjs" notice <文字>      # 记一条
node "$DSH_TOOLS/shared/shared.mjs" notices            # 看最近的
```

**通知 ≠ 派单。** 这是最容易搞混的地方：

| | 通知 | 派单 |
|---|---|---|
| 对方要做什么 | 只是知道 | **动手** |
| 要不要唤醒 | ❌ 不唤醒 | ✅ 必须 |
| 用什么工具 | `shared.mjs notice` | `dispatch-protocol` 的 `sentinel.mjs dispatch` |

**真实事故**：一天发 36 条"通知"，只有 8 条真的被执行——其余全躺在对方那儿。**执行率 8/36，而且没人知道那 28 条卡住了。**

**判据：需要对方动手，就用派单，不要用通知。**

---

## 总索引

```sh
node "$DSH_TOOLS/shared/shared.mjs" index
```

索引回答「东西在哪」——场景 ↔ 记忆 ↔ 技能。

**别提前建。** 他的建议是等有 3 个以上场景、且开始出现"同一个事实两处不一致"了再补。**过早建索引等于给自己加维护负担。**

---

## 什么时候用哪块

| 你想 | 用 |
|---|---|
| 记下待会要做的事 | 待办板 |
| 让别人知道我做完了什么 | 通知板 |
| 让**具体某个场景**去做某件事 | 派单（`sentinel.mjs dispatch`） |
| 找一份不知道放哪的文件 | 总索引 |

---

## 边界

- ⛔ **不要用通知代替派单** —— 那是最贵的浪费（对方不知道要动手）
- ⛔ **不要把待办当日志** —— 待办只放"还没做的"，做完就删
- ⛔ **不要过早建索引** —— 3 个场景以下用不着
- ⛔ **不要在待办里写"我昨天做了什么"** —— 那是通知，不是待办

每块板一混写，等于把它们又合并回去了。
