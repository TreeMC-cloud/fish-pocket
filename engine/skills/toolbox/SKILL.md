# 零件库

文件来源：移植自 mashanglinyu 的零件库实践（不要整包装，只拆需要的那一块）

一位实践者的做法：把网上能帮 DSH 改造的东西收进一个库，**需要啥直接读库，按需拿成品零件**。

> 他的原话：「我让 DSH 直接读库筛选出所有和记忆相关的插件，分析它们的逻辑，再对照我的记忆框架看哪些机制适合我，把适合的拿来。」

**核心理念：不要整包装，只拆你需要的那个功能。**

---

## 三个命令

```sh
node "$DSH_TOOLS/toolbox/toolbox.mjs" search <关键词> [--cat 分类] [--top N]
node "$DSH_TOOLS/toolbox/toolbox.mjs" show <名字或id>
node "$DSH_TOOLS/toolbox/toolbox.mjs" cats
```

检索搜名字、简介、作者，多个关键词用空格分隔（全部命中才算）。

## 什么时候该查

| 用户要什么 | 先查零件库 |
|---|---|
| 加一个新能力（记忆、搜索、图片处理…） | ✅ 八成有人做过 |
| 改界面外观 / 启动动画 | ✅ 有专门的分类 |
| 接一个新模型 / 服务 | ✅ 查 MCP 分类 |
| 修一个具体 bug | ❌ 自己查代码更快 |
| 用户说了明确要装哪个 | 直接 `show` 看细节 |

## 用的时候必须做的三件事

### 1. 先看，不要直接装

```sh
toolbox.mjs show <名字>
```

看这几个字段：

| 字段 | 说明 |
|---|---|
| **verify** | `5` = dsh.so 沙盒里真装过一次；`4` = 沙盒验证过；`0` = 未实测 |
| **risk** | `low` = 静态扫描没发现问题；空 = 没扫过 |
| **audited** | 本站是否看过真界面截图 |

**这三个字段都是 0 或空的，等于没人验过。** 要明确告诉用户这一点，不要说"这个能用"。

### 2. 拆，不要整装

他明确说过为什么：

> 「为什么不直接下个成品记忆插件？因为成品插件的机制是固定的，不符合我的要求。」

**正确做法**：
1. 读它的仓库，看它怎么实现的
2. 对照自己的需求，找出**哪一小块**适合
3. 只搬那一块，改成自己的

**不要**直接把别人的插件丢进 `cordis.patch.yml` 就完事——它的默认配置、命名空间、依赖都可能和你冲突。

### 3. 改完必须验证

装进去之后跑：

```sh
node "$DSH_TOOLS/self-review/selfcheck.mjs" --dir <改过的目录>
```

**「改坏了会报错」才是可验收的。** 他自己的原话：

> 「没改完一次，跑一套体检入口全查一遍，改坏了他自己会报错。改造的前提是你能验证他没坏，不然越改越乱。」

## 报告给用户时说什么

| ❌ 不要说 | ✅ 应该说 |
|---|---|
| 「这个插件能用」 | 「找到 3 个，其中 1 个在沙盒里真装过、低风险。它的做法是 X，我们可以只搬 X 那部分」 |
| 「装好了」 | 「改了 app/xxx.mjs 里的 20 行，selfcheck 通过。原作者的实现里还有 Y，我用不上就没搬」 |
| 「库里有 9000 个条目」 | 不要说这个，用户不关心数字 |

## 数据来源

集市：`https://www.mydsh.xyz/`（由 AI 检索整理，**上架 ≠ 实测通过**）

```sh
node "$DSH_TOOLS/toolbox/fetch-index.mjs"
```

（那个站点不太稳定，可能要跑几次。已有的数据不会丢。）

## 边界

- ⛔ **不要替用户决定装哪个** —— 把选项和风险说清，让他选
- ⛔ **不要整包搬运** —— 只拆需要的那一块
- ⛔ **没验证过的不说"能用"** —— 说"没人验过，要不要试"
