# 四层与三条不变量

文件来源：移植自 DeepSeek 官方 super-agent 设计原则（分层与三条不变量）

来自 DeepSeek 官方 super-agent 原型的核心设计。**放错层是系统退化的开始。**

---

## 四层（单向依赖，不能反向）

```
决策层   —— 谁来做、做什么、什么时候做（路由 / 授权 / 优先级）
   ↓
执行层   —— 真的动手（工具 / 文件 / 网络）
   ↓
验收层   —— 做完读回、对证据、判通过与否
   ↓
档案层   —— 一单一档：过程、证据、结论、可回滚点
```

**单向依赖的意思**：

| 越界行为 | 后果 |
|---|---|
| 执行层替决策层做判断（"我觉得这样更好就改了"） | 做了没人要的事，浪费注意力 |
| 验收层替执行层补动作（"顺手修了一下"） | 验收不再客观，自己验自己 |
| 档案层改前面的结论（"这个失败就不记了"） | 历史失真，无法回溯 |

**判据：发现自己在"补丁叠补丁"时，先问这件事该归哪一层，而不是继续加代码。**

---

## 三条不变量（比任何工具都重要）

### 1. 一单一 owner

**同一件事在同一时刻只有一个负责人。**

换人要**显式交接**，不能"两个人都以为对方在做"。

> 这是多 agent 系统里最贵的浪费：**双方都在等对方，而且没有任何报错。**

具体做法：
- 派活时明确说「这件事归你」
- 交接时明确说「现在归你了，我刚才做到 X」
- 不要让同一件事有两个"负责人"

### 2. 证据 > 声明

**说"做完了"不算，必须给可复核的证据。**

证据包括：读回的输出、日志、文件路径、URL、截图。

> 「活干完了但对方还不知道」= 没干完。
> 「只说好了」= 等于没说。

### 3. 人只批「解释 / 承诺 / 报价 / 新范围」

需要人点头的只有四类：

| 必须问人 | 不用问 |
|---|---|
| 怎么向客户解释 | 执行机械动作（读文件、跑命令） |
| 承诺什么、什么时间 | 按已有规则处理 |
| 报多少钱 | 格式调整 |
| 范围变没变 | 明显的错误修正 |

**不要为机械动作逐条找人确认** —— 那也是在浪费他的注意力。

## 七组概念（工作台里对应什么）

| 概念 | 一句话 | 在 App 里对应 |
|---|---|---|
| **Router / Worker** | 路由只分派，工人只做一类活；路由不干活 | 主会话 ↔ 子 agent / 远程工作台 |
| **Trigger / Thread** | 触发是"什么时候开始"，线程是"这一单的上下文" | 用户发消息 ↔ 一次任务的会话 |
| **Policy / Mandate** | 策略是规则，授权是这次允许做到哪 | 全局规矩 ↔ 单次任务的边界 |
| **Ticket / Assignment** | 工单是事实，指派是关系；一张单只能有一个 owner | todo 项 ↔ 派给谁做 |
| **Subscription / Outbox** | 订阅是"谁关心"，发件箱是"发出去的东西" | 交接文件 ↔ 派单记录 |
| **Inline & Spill** | 小结果直接回，大结果溢出到文件并留指针 | 短回复 ↔ 报告文件 |
| **Watchdog** | 看门狗只报"没动静"，不替人决定 | 超时提醒 ↔ 不问用户 |

## 实际用法

### 接到一个复杂任务时

```
1. 这件事该归哪一层？
   - 要不要做、做到什么程度 → 决策（问用户或按规则）
   - 具体怎么写 → 执行（做）
   - 做完对不对 → 验收（跑 selfcheck / 测试）
   - 记下来 → 档案（写进交接）

2. 派出去的话，owner 是谁？写清楚没有？

3. 回来的是声明还是证据？要证据。
```

### 发现"改了这里又坏了那里"

**这是放错层的信号。**

先停下来问：我是不是在执行层做了决策层的事？或者验收层在给执行层打补丁？

正确做法是把判断移回它该在的层，而不是继续加条件。

---

## 和自律检查的分工

- `self-review` 技能管**单次产物的质量**（引用、导出、结构、真的能跑）
- 这个技能管**整个流程的分层**（谁决定、谁做、谁验、谁记）

两个都要，缺一个都会出问题：只有 self-review 会做出"局部都对但整体乱"的系统；只有分层会做出"分层漂亮但每步都有 bug"的系统。
