# 成本守卫

文件来源：用户 2026-11-07：「所有都需要自动触发」+ 移植自 luanyujia-workbench 一-全局铁律 §2

**规矩不是写给人看的，是写给会犯错的机器看的。**

真实事故：**一晚几条 AI 互相写技术小论文，一个会话跑到 260 多轮，把账户余额烧到直接报错停摆。**

这不是意外，是设计缺失。没有边界，AI 之间的礼貌会无限放大。

---

## 三条硬上限

### 1. 往返次数

| 场景 | 上限 |
|---|---|
| 同一件事的消息数 | **≤3 条**（派单 + 回执 + 收尾知悉） |
| 子 agent 递归深度 | 默认 1 层，**不要随意加深** |
| 同一任务的重试 | **≤3 次**，之后必须换思路或问人 |

**收到回执就结束。** 不需要回复「收到，辛苦了」——那条消息不携带任何信息，只在烧钱。

### 2. 单条长度

- 派单/回执：≤200 字
- 聊天回复：默认一句，硬上限 100 词
- 细节放文件里，给路径

### 3. 批量任务分批

要做 N 个类似的事（转写 20 个视频、处理 100 个文件）时：

```
❌ 一次全跑完 —— 中途失败全丢，不知道跑到哪
✅ 先跑 3 个验证流程，再分批（每批 5-10 个），每批后检查
```

每批结束后确认：产物真的在、数量对、没有静默失败。

## 什么时候必须停手

看到这些信号，**立刻停**，不要"再试一次"：

| 信号 | 动作 |
|---|---|
| 余额/配额报错 | 立刻停，报告给用户 |
| 同一错误连续 3 次 | 停，说明尝试过什么，问人 |
| 上下文接近压缩线且压缩后仍超 | 停，写交接，开新会话 |
| 子 agent 反复超时 | 停，自己做或降级任务 |
| 产出越来越少 | 停，可能上下文被污染了 |

## 每轮都在烧的两笔固定开销

### MCP 工具定义

MCP 工具定义是每轮都注入的，**即使一次都没调用**。开销取决于工具数量：

| 规模 | 每轮开销 | 说明 |
|---|---|---|
| 本 App 的远程工作台（10 个小工具） | **约 1.2 千 token** | 实测：TOOLS 定义 5KB，加 JSON-RPC 包装约 1.1-1.4k |
| 完整的电脑操控 MCP 驱动（几十个工具） | **约 2 万 token** | 一位实践者提到的量级，工具多、schema 复杂 |

**所以"2 万"不是本 App 的数字，是他的场景**。本 App 开一个远程工作台约 1.2 千 token/轮，10 轮约 1.2 万——依然值得在不用时关掉。

**对策**：不用时关掉。App 的「设置 → 远程工作台」有开关，页面会显示当前开销。

### 技能索引

技能的名字 + 一句简介是常驻的，正文按需加载。这是合理的设计，但**技能多了索引也会膨胀**。

**对策**：技能数量控制在 10 个以内；单篇 SKILL.md 不超过 12KB，超了拆成主文件 + reference。

## 上下文越长越费钱

> **新的一轮会读旧轮次的内容，轮次越多，新的一轮消耗越多。**

所以：

1. **记忆放单独文件**，不要靠对话历史
2. **轮次多了就开新会话**，把进度写进交接
3. **主动换会话**（在上下文变脏之前），不要等引擎压缩

> 他的原话：「该换会话就换会话，用一次干净的开始，把模型的聪明劲拉回来。引擎的自动压缩是安全网，不是我的主策略。」

## 两个工具：派活前查负载，干活时盯轮次

### 派活前：现在能不能再派

```sh
node "$DSH_TOOLS/cost-guard/load.mjs" check
```

退出码 0 = 能派，1 = 别派（会给出具体理由，如「可用内存 412MB / 4096MB，低于 15% 红线」）。

在 iOS 上这条尤其重要：**手机内存被系统严格限制，多个子 agent 并行容易被静默杀掉**——表现为「App 突然回到桌面」，用户完全不知道发生了什么。

### 干活时：是不是该换会话了

```sh
node "$DSH_TOOLS/cost-guard/turns.mjs" tick          # 每轮记一次
node "$DSH_TOOLS/cost-guard/turns.mjs" status        # 看还剩多少余量
node "$DSH_TOOLS/cost-guard/turns.mjs" reset --reason "已交接"   # 换会话后归零
```

三条红线（可用环境变量改）：**40 轮 / 20 万 token / 3 小时**。超了退出码 1，并提醒先写交接再换。

**为什么 40 轮**：轮次越多，每一轮都要把历史重新读一遍。40 轮后，重复读取的成本已经超过任务本身。

### 什么时候**必须**调（不是想起来才调）

工具不会自己跑，所以时机要写死。这四个时刻**不许跳过**：

| 时刻 | 调什么 |
|---|---|
| 准备派活给子 agent / 远程工作台之前 | `load.mjs check` —— 负载高就先别派 |
| 每完成一轮实质性工作 | `turns.mjs tick` —— 不记就不知道跑了多少轮 |
| 开始新工作前 | `sentinel.mjs awaited` —— 先看有没有人在等我 |
| 每次派完活隔一阵 | `sentinel.mjs open` —— 看有没有人没回 |

**这几个时刻的定义是硬的，不是"视情况"。** 没有写死时机的规矩，三个月后一定退化成"想起才做"。

> 更彻底的做法是把它做成插件（程序自动触发）。目前是 CLI + 硬性时机，已经比"靠自觉"强；等哪天发现还是经常忘记，再升级成插件。

## 派活前先算账

动手前问三句：

1. **这件事值得派出去吗？** 一两步能做完的，自己更快
2. **派出去之后我怎么知道结果？** 不知道就别派（会变成哑弹）
3. **最坏要跑多少轮？** 超过 3 轮的设计有问题

## 自检

- 我是不是在"等对方"而没有主动查结果？（异步任务是黑洞）
- 我这条消息携带信息吗？没有 → 别发
- 这个循环有出口吗？没有 → 别开始
