# 成本守卫

**规矩不是写给人看的，是写给会犯错的机器看的。**

真实事故：**一晚几条 AI 互相写技术小论文，一个会话跑到 260 多轮，把账户余额烧到直接报错停摆。**

这不是意外，是设计缺失。没有边界，AI 之间的礼貌会无限放大。

---

## 三条硬上限

### 1. 往返次数

| 场景 | 上限 |
|---|---|
| 同一件事的消息数 | **≤3 条**（派单 + 回执 + 收尾知悉） |
| 子 agent 递归深度 | 默认 1 层，**不要随意加深** |
| 同一任务的重试 | **≤3 次**，之后必须换思路或问人 |

**收到回执就结束。** 不需要回复「收到，辛苦了」——那条消息不携带任何信息，只在烧钱。

### 2. 单条长度

- 派单/回执：≤200 字
- 聊天回复：默认一句，硬上限 100 词
- 细节放文件里，给路径

### 3. 批量任务分批

要做 N 个类似的事（转写 20 个视频、处理 100 个文件）时：

```
❌ 一次全跑完 —— 中途失败全丢，不知道跑到哪
✅ 先跑 3 个验证流程，再分批（每批 5-10 个），每批后检查
```

每批结束后确认：产物真的在、数量对、没有静默失败。

## 什么时候必须停手

看到这些信号，**立刻停**，不要"再试一次"：

| 信号 | 动作 |
|---|---|
| 余额/配额报错 | 立刻停，报告给用户 |
| 同一错误连续 3 次 | 停，说明尝试过什么，问人 |
| 上下文接近压缩线且压缩后仍超 | 停，写交接，开新会话 |
| 子 agent 反复超时 | 停，自己做或降级任务 |
| 产出越来越少 | 停，可能上下文被污染了 |

## 每轮都在烧的两笔固定开销

### MCP 工具定义

**默认打开一个 MCP 驱动 = 每轮固定消耗约 2 万 token**（官方原型的实测数字）。

即使一次都没调用，这些工具的说明也要每轮重新告诉模型。

**对策**：不用时关掉。App 的「设置 → 远程工作台」有开关，页面会显示当前开销。

### 技能索引

技能的名字 + 一句简介是常驻的，正文按需加载。这是合理的设计，但**技能多了索引也会膨胀**。

**对策**：技能数量控制在 10 个以内；单篇 SKILL.md 不超过 12KB，超了拆成主文件 + reference。

---

## 上下文越长越费钱

> **新的一轮会读旧轮次的内容，轮次越多，新的一轮消耗越多。**

所以：

1. **记忆放单独文件**，不要靠对话历史
2. **轮次多了就开新会话**，把进度写进交接
3. **主动换会话**（在上下文变脏之前），不要等引擎压缩

> 他的原话：「该换会话就换会话，用一次干净的开始，把模型的聪明劲拉回来。引擎的自动压缩是安全网，不是我的主策略。」

---

## 派活前先算账

动手前问三句：

1. **这件事值得派出去吗？** 一两步能做完的，自己更快
2. **派出去之后我怎么知道结果？** 不知道就别派（会变成哑弹）
3. **最坏要跑多少轮？** 超过 3 轮的设计有问题

---

## 自检

- 我是不是在"等对方"而没有主动查结果？（异步任务是黑洞）
- 我这条消息携带信息吗？没有 → 别发
- 这个循环有出口吗？没有 → 别开始
