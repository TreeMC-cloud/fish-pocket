# 派单与回执 —— 多 Agent 协作里最贵的浪费是"双方都在等对方"

文件来源：移植自 luanyujia-workbench 三-跨场景协作（回执闭环三条铁律）

这个浪费**没有任何报错**。你以为交出去了，对方以为没收到，最后活没干、两边都觉得委屈。

---

## 第一件事：分清「派单」和「通知」

| | 派单 | 通知 |
|---|---|---|
| 对方要做什么 | **动手** | 只是知道 |
| 判据（看句子就知道） | 「请你改 / 做完回一句 / 改完跑 xx 复验」 | 「以后就这么办 / 请注意一下」 |
| 预期回复 | 一条**带证据**的回执 | 无 |

**最容易犯的错**：把需要动手的活写成了通知式的句子，对方收到后不当回事。

> 真实数据：一天发 36 条"通知"，只有 8 条真的被执行 —— 其余全躺在对方那儿等着，**执行率 8/36，而且没人知道那 28 条卡住了**。

改法：需要动手就用祈使句，并明确要求回执。

---

## 第二件事：派单必须写清四件（缺一件对方就得追问一轮）

```
① 现象    ：现在是什么样子（可观察的，不要形容词）
② 照哪做  ：看哪个文件哪一节 / 用哪个工具（唯一出处，别让对方猜）
③ 怎么验  ：做完跑什么检查、看到什么算通过
④ 回一句  ：明确要回执，写明"我在等你的回执"
```

对照：

| | 写法 |
|---|---|
| ❌ | 「代码有点乱，你整理一下」 |
| ✅ | 「`selfcheck.mjs` 在 src/ 报 3 个 I1 引用错误（a.mjs/b.mjs/c.mjs）。按 `self-review` 技能里 I1 那条修，路径要指向真实文件。修完跑 `node selfcheck.mjs --dir src` 应为 0 错误。**我在等你的回执。**」 |

---

## 第三件事：回执必须带证据

格式：

```
结论：<做完了什么>
证据：<命令输出 / 文件路径 / 关键行>，差异集合 = <到底改了几处>
落盘：<文件路径>
```

**三条硬规矩：**

- ⛔ **只说「好了」等于没说** —— 没有证据的完成，是在要求对方相信你
- ⛔ **只在自己这边说「我做完了」= 没交付** —— 判据是「对方知道了」，不是「我说了」
- ⛔ **收到「知悉」不许回** —— 回了就开新一条线，双方客气到烧钱

> 判据：**「活干完了但对方还不知道」= 没干完。**

---

## 第四件事：给异步任务留"未回执"状态

`subagent` 和 `wb_submit_task` 都是**异步**的：它们立刻返回一个 id，活还在后台跑。

**不要**在拿到 id 后就对用户说「做好了」。正确顺序：

1. 拿到 id，告诉用户「已提交，在跑」
2. 自己记下这个 id（写进交接文件，或在 todo 里）
3. 隔一会儿用 `wb_task_status` / 子 agent 的完成通知查结果
4. 拿到结果后，把**真实的验收输出**转告用户

**没有"未回执"这个状态，派单就等于扔进黑洞** —— 你会以为在跑，实际上早就失败了。

---

## 第五件事：限制往返次数

| 上限 | 值 |
|---|---|
| 同一件事的消息数 | **≤3 条**（派单 + 回执 + 收尾） |
| 单条长度 | ≤200 字 / ≤10 行，细节放文件里 |
| 纯确认语 | ⛔ 不许发（收到 / 好的 / 谢谢，不携带任何信息） |

实测：AI 之间会无限礼貌，"好的""收到""请确认是否已确认"能来回几十轮，一天烧掉几十万 token。

**收到回执就结束。** 不需要回复「收到，辛苦了」。

---

## 用台账把"谁欠谁"变成可查的

规矩写在纸上靠自觉，做成工具才靠得住。派单之后立刻记一条：

```sh
node "$DSH_TOOLS/dispatch-protocol/sentinel.mjs" dispatch --to <谁> --what <做什么> --expect <预期回执>
```

两个查询，回答两个问题：

| 查什么 | 回答 | 什么时候查 |
|---|---|---|
| `open` | **我发出、还没人回的**（我欠不欠催？） | 每次派完隔一阵 |
| `awaited` | **别人在等我回的**（我是不是让别人空等？） | 开始新工作前 |

销账：`sentinel.mjs ack --id <id> --evidence "命令输出/文件路径"`

**两个查询有问题时退出码是 1**，没问题才是 0 —— 这样"有没有人卡着"能进脚本判断，不是靠人想起来看。

> 没有台账的派单，等于没派。**"我发出没回"这个状态不存在，派单就等于扔进黑洞。**

## 什么时候不该派单

| 情况 | 为什么 |
|---|---|
| 一两步就能做完 | 写四件套的时间比自己做还长 |
| 需要用户中途确认 | 子 agent 无法跟用户对话 |
| 依赖本对话的细节 | 子 agent 看不到这段上下文，会做错 |
| 只是查个东西 | 自己搜比派单快 |

判据：**「这件事需要它动手，而且我能把要做的事完全说清」** —— 两个都成立才派。
