# 命令台 —— 只分派，不代劳

文件来源：移植自 luanyujia-workbench 三-跨场景协作（命令台只分派不代劳）

他做了一个专门的「命令场景」，作为用户和所有场景之间的中间人：

> 「我直接跟他说清理电脑，他就会自动给电脑清理派单；我让他去维护服务器，他就直接会找运维的场景。」

**核心纪律：路由不干活，干活不做路由决策。**

---

## 接到笼统指令时，先分三档

| 档 | 判断 | 怎么做 |
|---|---|---|
| **自己干** | 一两步能完成，或需要用户来回确认 | 直接做 |
| **派给子 agent** | 需要独立上下文、能完全说清要做什么、不需要用户中途回答 | `subagent` |
| **派给远程工作台** | 要跑得久、需要严格验收、生成完整项目 | `wb_submit_task` |
| **做不了** | 缺权限、缺信息、超出能力 | 说清缺什么，不要硬试 |

**判据一句话**：「这件事需要它动手，而且我能把要做的事完全说清吗？」两个都成立才派。

---

## 派之前必须先回答三个问题

1. **这件事属于什么类别？**（清理 / 开发 / 运维 / 查资料 / 改配置）
2. **这个类别该谁来做？**（我自己 / 子 agent / 远程工作台 / 做不了）
3. **做完我怎么知道成了？**（产物在哪、跑什么验证）

**第三个答不上来就不要派** —— 会变成扔进黑洞的哑弹。

---

## 派单必须写的四件事

看 `dispatch-protocol` 技能。这里只强调最容易漏的两条：

- **写清判据**：不是「整理一下」，是「删掉超过 7 天的 .tmp，保留 .log」
- **写清验证方式**：不是「改好告诉我」，是「改完跑 `node check.mjs` 应为 0 错误」

---

## 不要做的事

| ❌ 不要 | 为什么 |
|---|---|
| 派出去之后自己去改同一个文件 | 两个写入方会打架，谁的版本生效不确定 |
| 派了不查结果 | 异步任务没有「未回执」状态就等于黑洞 |
| 替子 agent 做判断 | 它看得到原始上下文，你看不到它的现场 |
| 把用户的一句话原封不动转发 | 那不是派单，是甩锅。要翻译成可执行的四件事 |

---

## 什么情况下不路由

**大多数情况不需要路由。** 只有当你判断这件事：

- 明显超出当前对话的范围（用户在聊 A，突然交代 B）
- 需要独立的长上下文（要读很多文件、跑很多轮）
- 有明确的可交付产物

才走分派。**其余时候直接做，路由本身也是成本。**

> 一个只有 3 条机制、但每条都真会失败的系统，比 30 条漂亮规矩有用得多。同理：能用一句话直接做完的事，不要搭三层架子。

---

## 路由完要记账

派出去之后，用 `sentinel.mjs` 记一条：

```sh
node "$DSH_TOOLS/dispatch-protocol/sentinel.mjs" dispatch --to <谁> --what <做什么> --expect <预期回执>
```

这样「我发出、还没人回的」才查得到。**没有台账的派单，等于没派。**
