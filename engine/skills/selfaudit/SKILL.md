# 规矩体检

**核心理念：没有"会失败的检查"的规矩 = 一句口号。**

规矩写在文档里靠自觉，机制跑在代码里靠机器。一份只有规矩的系统，三个月后一定退化成「看心情」。

---

## 怎么跑

```sh
node "$DSH_TOOLS/selfaudit/selfaudit.mjs" <工作目录>
node "$DSH_TOOLS/selfaudit/selfaudit.mjs" --json <工作目录>
```

脚本在只读的 app bundle 里，不在你的工作目录下，所以必须用 `$DSH_TOOLS` 这个环境变量拼绝对路径。直接写 `node selfaudit.mjs` 会报找不到模块。

退出码 0 = 全过，1 = 有问题（**这个非 0 很重要，它让检查真的会失败**）。

---

## 它检查什么

| 编号 | 规矩 | 违规长什么样（可判定的） |
|---|---|---|
| **R1** | 交接文件存在且合格 | 没有 `HANDOFF.md`，或缺五小节，或「下一步」写成「继续开发」这种虚话 |
| **R2** | 交接体量 ≤4KB | 超了就说明在写周报，不是写交接 |
| **R3** | 目录卫生 | 堆了 `.bak` / `.tmp` / `.orig` / `副本` 这类临时残留 |
| **R4** | 技能体量 | 单篇 SKILL.md 超 12KB，应该拆成主文件 + reference |

**每条都输出差异集合**，不是只给一个 0/1：

```
✗ [R3] 目录卫生  3 个临时残留：app.mjs.bak, test.tmp, 副本.json
     → 临时文件和备份不该留在工作目录。要留证据就改名放 evidence/。
```

---

## 五步法：任何规矩要变成机制，都得走这五步

```
第 1 步  写清"违规长什么样"
         ❌「索引要完整」    ✅「文件存在但索引里没这一行」

第 2 步  找到唯一的判据出处
         ⛔ 两处判据 = 两份结论 = 早晚打架

第 3 步  写一个能 exit 非 0 的检查
         输出必须能说出"差异集合"，不是只给 0/1

第 4 步  给它一个"应当失败的反例"
         ⛔ 90% 的人会漏这一步，也是最容易自欺的地方
         判据：反例不报 = 这个检查是假的

第 5 步  挂到节奏上
         手动跑的检查等于没跑。挂进"每次改完必跑"的流程。
         ⛔ 失败的输出要进待办，不能只躺在日志里
```

---

## 什么不该变成机制

三种情况留在「规矩」层是对的：

| 情况 | 为什么 |
|---|---|
| **判断类**（好不好、该不该做） | 没有客观判据，硬写成检查会误杀 |
| **一次性**（这次这样，下次不一定） | 写机制的成本高于收益 |
| **靠人拍板**（要不要花钱、要不要对外） | 机制负责**提醒**，不负责**决定** |

**判据：这条规矩能不能写成「条件 + 差异集合」？** 能 → 机械化；不能 → 留在规矩层，但要写清「谁来判」。

---

## 一条真的落地了的规矩，要能回答五个问题

```
① 违规长什么样？            （可判定的现象）
② 谁在判？                  （唯一出处）
③ 不通过时输出什么？        （差异集合，不是 0/1）
④ 怎么证明它真的会报？      （反例）
⑤ 多久跑一次？失败进哪？    （节奏 + 去向）
```

五条答不全，它还停在「口号」阶段。

---

## 别把机制化当目标

它是**手段**：目的是**让人不用记规矩，机器替你盯**。

> 一个只有 3 条机制、但每条都真会失败的系统，比 30 条漂亮规矩有用得多。
