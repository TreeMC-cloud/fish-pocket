# 远程工作台

两种工作模式，取决于用户是否在「设置 → 远程工作台」填了服务器地址：

- **纯本地**（默认）：引擎和模型都在这台 iPhone 上跑，零外部连接，远程工具不存在。
- **已连接**：工具列表里多出 `mcp__workbench__*` 一组，重活可以交给服务器。

**先确认工具在不在**：`mcp__workbench_*` 没出现，说明没配或连不上。这时**完全按纯本地正常工作**，不要提示用户去配置，也不要因为"本来能交给服务器"而停下。

## 工具索引（只用时查，不要全记住）

| 工具 | 一句话 |
|---|---|
| `wb_submit_task` | 提交需求，异步返回 id |
| `wb_task_status` | 查任务详情：阶段、门禁结果、产物路径 |
| `wb_list_tasks` | 列任务，可按 state 过滤 |
| `wb_move_task` | 移动看板状态 |
| `wb_memory_search` | 搜长期记忆 —— 动手前先搜 |
| `wb_memory_save` | 存一条经验结论 |
| `wb_list_skills` | 列已沉淀的技能模板 |
| `wb_stats` | 任务/记忆/技能数、今日消耗 |
| `wb_health` | 探测可达性 |
| `wb_evolve_advice` | 系统自评的短板 |

## 什么时候交给远程

判断标准是**执行成本和验收强度**，不是任务看起来大不大：

| 情况 | 处理 |
|---|---|
| 生成完整可运行的项目（网页/脚本/工具） | 远程，`wb_submit_task` |
| 需要严格验收：真跑起来、契约检查、产物真实性 | 远程，它的交付链有门禁 |
| 云端可能积累过同类经验 | 先 `wb_memory_search` / `wb_list_skills` |
| 改一个文件、跑一条命令、回答问题 | **本地做**，别绕远程 |
| 要访问手机本地文件、相册、剪贴板 | **本地做**，远程碰不到 |

## 提交任务后必须做的

`wb_submit_task` 立刻返回 id，任务还在 `triage`。**不要**对用户说"已经做好了"：

1. 记下 id，告诉用户「已提交，在跑」
2. 稍后用 `wb_task_status` 查进度
3. 把 `gate.checks` 里**真实的验收结果**转告用户
4. 到 `done` 时给出 `outputs` 里的产物路径
5. 到 `blocked` 时说明 `gate` 哪一项没过，不要只说"失败了"

## 使用的完整规矩

派单怎么写在 `dispatch-protocol` 技能里（四件套 + 回执带证据 + 别无限往返）。提交远程任务本质上就是一次派单，那些规矩同样适用，尤其是：

- **没有"未回执"状态，派单就等于扔进黑洞** —— 必须主动查结果
- **只说「好了」等于没说** —— 转告用户时要给证据（产物路径、验收输出）

## 分工原则

**把"跑得久、验得严"的给服务器，把"碰得到设备、来回快"的留本地。**

典型组合：用户要在手机上做个工具并装上用 ——

1. 本地：搞清楚需求，读用户手机里的现有文件
2. 远程：`wb_submit_task` 让交付链生成并验收
3. 本地：把产物取到手机上，帮用户用起来
