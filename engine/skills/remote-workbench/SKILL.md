# 远程工作台

这个 App 有两种工作模式，取决于用户是否在「设置 → 远程工作台」里填了服务器地址：

- **纯本地**（默认）：引擎和模型都在这台 iPhone 上跑。没有任何对外连接。远程工具不存在。
- **已连接**：Agent 的工具列表里多出 `mcp__workbench__*` 这一组，重活可以交给服务器。

**先确认工具在不在**：如果 `mcp__workbench_*` 系列工具没有出现在你的工具列表里，说明用户没配远程工作台，或者配了但连不上。这时**完全按纯本地方式正常工作**，不要提示用户去配置，也不要因为"本来能交给服务器"而停下。

## 什么时候该交给远程工作台

判断标准是**执行成本和验收强度**，不是任务看起来大不大：

| 情况 | 处理 |
|---|---|
| 要生成一个完整可运行的项目（网页、脚本、小工具） | 交给远程，`wb_submit_task` |
| 需要严格验收：真跑起来、契约检查、产物真实性 | 交给远程，它的交付链有门禁 |
| 云端已有积累的记忆或技能，很可能踩过同样的坑 | 先 `wb_memory_search` 或 `wb_list_skills` |
| 改一个文件、跑一条命令、回答一个问题 | **本地做**，别绕远程 |
| 需要访问手机本地文件、相册、剪贴板 | **本地做**，远程碰不到这些 |

## 工具速查

| 工具 | 用途 | 注意 |
|---|---|---|
| `wb_submit_task` | 提交需求，返回任务 id | **异步**：它只受理，不等待结果。别把它当同步调用 |
| `wb_task_status` | 查单个任务：阶段、门禁结果、产物路径 | 提交后隔一会儿再查 |
| `wb_list_tasks` | 列任务，可按 state 过滤 | state: triage/todo/doing/review/done/blocked |
| `wb_move_task` | 移动看板状态 | 用户要改优先级或重排队时用 |
| `wb_memory_search` | 搜过去的经验 | **动手前先搜**，尤其是踩坑类问题 |
| `wb_memory_save` | 存一条经验 | 一条一件事，写清结论，别存流水账 |
| `wb_list_skills` | 列出已沉淀的做法模板 | 做新需求前先看有没有现成的 |
| `wb_stats` / `wb_health` | 服务状态 | health 用来确认"到底连没连上" |
| `wb_evolve_advice` | 系统自评的短板 | 用户问"这套系统有什么问题"时才用 |

## 提交任务后必须做的

`wb_submit_task` 立刻返回一个 id，任务还在 `triage` 状态。**不要**告诉用户"已经做好了"。正确做法：

1. 记下返回的 `id`，告诉用户任务已提交、服务器开始处理
2. 稍后用 `wb_task_status` 查进度，把 `gate.checks` 里真实的验收结果转告用户
3. 任务到 `done` 时，把 `outputs` 里的产物路径告诉用户
4. 到 `blocked` 时，说明 `gate` 里哪一项没过，不要只说"失败了"

## 分工的原则

**把"跑得久、验得严"的活给服务器，把"碰得到设备、来回快"的活留在本地。**

一个典型组合：用户要在手机上做个工具并装上用。

1. 本地：搞清楚需求，读用户手机里的现有文件
2. 远程：`wb_submit_task` 让交付链生成并验收这个项目
3. 本地：把交付回来的产物取到手机上，帮用户用起来

不要让服务器去干只有手机能做的事，也不要让手机硬扛需要编译、跑测试、批量处理的重活。
