# BENCH-001 基线（2026-11-09）

> 这份文件存在的唯一目的：让「变快了 / 变慢了 / 领先了」有数字可对。
> 没有基线的优化是猜测，没有重复测量的结论不可复现。

跑法：

```bash
cd engine && node runtime/bench.mjs --tasks 200
```

## 测得的环境

- 设备：iPhone（iOS，iSH/Alpine 内核）
- 引擎：Node v22.23.4，单进程
- 存储：App 沙盒内文件系统
- 时间：2026-11-09

**这些数字只代表本进程的文件 IO 与调度开销。** 真实模型响应、网络往返、
DSH session 并行都不在其中——拿它宣称「端到端性能」是错的。

## 基线数字（优化后，2026-11-09）

第一轮基线是优化前测的，一并保留作对比。

| 项目 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 任务生命周期（200 个） | 17.3 ms | 22.4 ms | +29%（测量噪声，见下） |
| 任务建表（纯内存，200 个） | 7.2 ms | 7.9 ms | 持平 |
| 幂等去重（200 条重复） | 1.5 ms | 1.9 ms | 持平 |
| **调度底噪（任务零耗时）** | **130.4 ms** | **90.6 ms** | **-31%** |
| 并发调度 1 | 230 ms | 213.6 ms | -7% |
| 并发调度 4 | 123.7 ms | 86.3 ms | **-30%** |
| 并发调度 20 | 125.6 ms | 78.3 ms | **-38%** |

## 做了什么优化

**给 `task-registry.load()` 加了文件状态校验缓存**（`mtime + size`）。

原因：`router.runOne` 每个任务要调 2-3 次 `state()`，每次都是一次完整
`readFileSync` + `JSON.parse`。20 个任务 = 40-60 次读盘，而且文件随任务数
增长越来越大，是 **O(n²)** 劣化。

为什么用文件时间戳而不是纯内存：CLI（`task-registry.mjs list`）和别的进程
也会写这个文件，只信内存会读到陈旧状态。已做负向验证——往文件里手写一条
外部任务，`load` 能立刻发现。

**未验证的假设被推翻了**：原本以为「并发 20 比并发 4 慢」是写盘争用，
优化后发现并发 20（78.3ms）反而最快。真实原因是重复读盘，
读的次数在并发低时更密集。

## 剩余成本拆解

| 操作 | 耗时 |
|---|---|
| 20 次 `save`（writeFileSync + rename） | 36.1 ms |
| 40 次 `load`（走缓存后） | 4.6 ms |
| 20 次纯 `writeFileSync`（不 rename） | 10.8 ms |

`rename` 占 `save` 的约 70%（36.1 − 10.8 = 25.3 ms）。
**这个代价必须留着**——原子写是「崩溃时不留半个 JSON」的唯一保证，
省掉它换来的是数据损坏风险。

## 怎么读这组数

**1. 底噪 130ms 才是瓶颈，不是调度。**

「调度底噪」这一行是任务体完全不做事时的耗时。20 个任务要 130ms，
说明成本几乎全在 **每次状态转移的同步落盘**（`transition` → `save`），
不在任务执行上。

对照组：并发 1 + 任务 5ms → 230ms，比底噪多 100ms ≈ 20 × 5ms，正好是任务本身的时间。
一旦并发打开（4 或 20），任务时间被 IO 完全淹没。

**2. 并发 4 是最优，不是 20。**

| 并发 | 耗时 |
|---|---|
| 1 | 230 ms |
| 4 | 124 ms |
| 20 | 126 ms |

超过 4 之后不再变快（20 甚至略慢），因为瓶颈已经变成写盘争用。
**这意味着 `DEFAULT_MAX_CONCURRENT` 取 4 左右是合理的**，调大没有收益。

**3. 幂等去重很便宜（8 µs/条）。**

webhook 重投是常态，这个成本可以接受，不需要额外的去重索引。

## 什么时候该重跑

- 改了 `task-registry.mjs` 的 `save` / `load` / `transition`
- 改了 `router.mjs` 的调度逻辑
- 想宣称「性能提升」之前（必须先有前后两组数）

## 已知可优化项（按性价比）

1. **批量落盘**：现在每次 `transition` 都同步 `writeFileSync + rename`。
   同一轮里连续多次转移（`received→queued→running`）可以合并成一次写。
   预期能把底噪从 130ms 降到 20-30ms。**这是目前最大的一块。**
2. **写盘改用追加日志 + 定期快照**：状态机事件追加到 JSONL，
   定期 compaction 成快照。崩溃恢复更可靠，写也更便宜。
3. `PRIORITY` 排序在任务多时是 O(n log n)，但相对 IO 可忽略，先不动。

## 不测什么（诚实声明）

- **模型响应时间**：取决于 provider，与系统能力无关
- **真实 DSH session 并行**：需要多个 agent 同时跑，当前版本做不到（单 Worker）
- **网络往返**：诊断上报、模型调用都不测
- **端到端任务完成率**：需要真实任务集和验收标准，属于后续 BENCH-002

`BENCH-002`（端到端质量基准）还没写。在那之前，任何「领先 N 个版本」的说法都没有依据。
